# GitManager desktop build matrix

GitManager is a Tauri desktop application. Its supported build targets are therefore the desktop targets supported by the current Tauri/Rust/WebView stack, not every operating system or CPU architecture on which the Git command-line program itself can run.

## Supported desktop targets

| Platform | Architecture | Rust target | Windows compatibility |
| --- | --- | --- | --- |
| Windows | x64 | `x86_64-pc-windows-msvc` | Windows 10 and 11 |
| Windows | x86 | `i686-pc-windows-msvc` | 32-bit app for compatible Windows 10/11 x64 systems |
| Windows | ARM64 | `aarch64-pc-windows-msvc` | Windows 11 ARM64 |
| Linux | x64 | `x86_64-unknown-linux-gnu` | GTK/WebKitGTK distributions |
| Linux | ARM64 | `aarch64-unknown-linux-gnu` | GTK/WebKitGTK distributions |
| Linux | ARMv7 (32-bit) | `armv7-unknown-linux-gnueabihf` | GTK/WebKitGTK distributions; DEB/RPM bundles |
| macOS | Intel x64 | `x86_64-apple-darwin` | Intel Macs |
| macOS | Apple Silicon ARM64 | `aarch64-apple-darwin` | Apple Silicon Macs |

Windows 10 and Windows 11 are compatibility labels, not different CPU targets. For example, `windows(10,x64)` and `windows(11,x64)` compile the same x64 executable. The x86 target is a 32-bit application target; Windows 11 itself is not a 32-bit operating system.

Linux distribution packages are generated by Tauri for the selected Linux architecture. The ARMv7 Linux job cross-compiles against ARM hard-float WebKitGTK and publishes DEB/RPM packages; AppImage is omitted for that cross-target because it requires a QEMU runtime. The current matrix does not claim support for every BSD, Solaris, embedded, or server architecture supported by Git itself: those platforms need a compatible Tauri desktop WebView and native dependency stack first.

Linux release artifacts currently build on Ubuntu 22.04 to keep the glibc/WebKitGTK baseline compatible with older supported distributions. GitHub has announced retirement of its Ubuntu 22.04 hosted runner image for April 17, 2027; before that date, move the Linux build jobs to a Debian 12-based container or another pinned older sysroot rather than blindly switching to Ubuntu 24.04.

## Build commands

The default build selection is all platforms and architectures, with installer packaging enabled:

```powershell
# Dispatch every supported target, wait for GitHub Actions, then download artifacts
py build.py

# Same as the default
py build.py --build=all --type=installer

# Build only one platform group through native GitHub Actions runners
py build.py --build=windows --type=installer
py build.py --build=linux --type=installer
py build.py --build=macos --type=installer

# Build one exact target locally when the current machine has the matching toolchain
py build.py --build='windows(10,x64)' --type=installer
py build.py --build='windows(11,x86)' --type=app
py build.py --build='linux(arm64)' --type=app
py build.py --build='linux(armv7)' --type=installer
py build.py --build='macos(x64)' --type=installer
```

The short one-dash spellings are also accepted:

```powershell
py build.py -build=all -type=installer
py build.py -build='windows(11,x86)' -type=app
```

- `--build=all`, `--build=windows`, `--build=linux`, and `--build=macos` dispatch the matrix workflow through the GitHub CLI.
- Authenticate the GitHub CLI first with `gh auth login`. The current branch must be pushed to GitHub. The matrix workflow must exist on the repository's default branch before GitHub will accept manual workflow dispatch.
- An exact target selector builds locally when the host toolchain supports it. If the current machine cannot build that platform or architecture, the script automatically dispatches only that exact target to its native GitHub Actions runner.
- `--type=installer` is the default and creates the platform's Tauri bundles/installers. `--type=app` uses Tauri's `--no-bundle` mode and publishes the application and its required sidecar executables without installer packaging.
- `--debug` selects debug binaries; release builds are the default.

## Output layout

All Cargo build output is redirected away from the repository-root `target/` directory:

```text
build/
  .rcache/                 # Cargo/Rust compilation cache and intermediate files
  dist/
    windows-x64/
      app/                 # GitManager, gitm, setup, crash-helper and service binaries
      installer/           # NSIS setup.exe, WiX MSI and MPDEV comparison MSI
      build-manifest.json
    windows-x86/
      app/                 # 32-bit app and sidecar binaries
      installer/           # NSIS setup.exe and WiX MSI
      build-manifest.json
    windows-arm64/
      app/                 # ARM64 app and sidecar binaries
      installer/           # NSIS setup.exe and WiX MSI
      build-manifest.json
    linux-x64/
      app/                 # Native app and sidecar binaries
      installer/           # DEB, RPM, AppImage and app bundle outputs
      build-manifest.json
    linux-arm64/
      app/                 # ARM64 app and sidecar binaries
      installer/           # DEB, RPM, AppImage and app bundle outputs
      build-manifest.json
    linux-armv7/
      app/                 # ARMv7 app and sidecar binaries
      installer/           # ARMv7 DEB and RPM packages
      build-manifest.json
    macos-x64/
      app/                 # Intel macOS app and sidecar binaries
      installer/           # DMG and app bundle outputs
      build-manifest.json
    macos-arm64/
      app/                 # Apple Silicon app and sidecar binaries
      installer/           # DMG and app bundle outputs
      build-manifest.json
```

Installer builds publish both the app/sidecar binaries and installer bundles. App-only builds publish just the `app/` directory. The all-platform command downloads GitHub Actions artifacts into `build/dist/`; each downloaded artifact is kept in its own `gitmanager-<target>` directory.

The generated `build/` directory is ignored by Git. It is safe to delete when no build is running; doing so removes cached compilation output and previously downloaded build artifacts.

## Linux runtime smoke test

`.github/workflows/runtime_launch_test.yml` builds the Linux x64 application without bundling, verifies its shared-library dependencies, then launches the actual Tauri UI under Xvfb and a D-Bus session. It seeds twelve small local Git repositories and configures GitManager to scan them on startup.

The workflow records launch logs and `/usr/bin/time -v` resource metrics. A launch that exits before the 45-second observation window fails, as does an unresolved shared library or peak resident memory above 1.5 GiB. The diagnostic log and dependency report are uploaded even when the test fails.

## Git command-line tools

GitManager uses its built-in `libgit2` engine for local repository discovery and core Git data. Git CLI is not required merely to scan repositories. GitHub CLI (`gh`) is an optional account-integration helper, not a replacement for Git.

If neither `git` nor `gh` is found at startup, GitManager asks whether to continue with the scan. Choosing Continue keeps the built-in Git engine available; choosing Close exits the application. Commands that explicitly launch Git or GitHub CLI remain unavailable until their respective tool is installed.
